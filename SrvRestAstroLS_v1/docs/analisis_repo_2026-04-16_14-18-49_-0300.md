## Hallazgos principales

### 1. Entrypoint operativo inconsistente en documentacion

- El README del backend indica arrancar con `uv run python ls_iMotorSoft_Srv01.py`.
- Ese entrypoint monta solo un subconjunto minimo de rutas.
- La app demo real que expone `orquestador`, `workflow`, `AI workflow`, `messaging`, `SSE` y `crm` es `ls_iMotorSoft_Srv01_demo.py`.

Impacto:

- Es facil levantar el binario equivocado y concluir que faltan rutas o que el backend "no anda".

Referencias:

- `SrvRestAstroLS_v1/backend/README.md`
- `SrvRestAstroLS_v1/backend/ls_iMotorSoft_Srv01.py`
- `SrvRestAstroLS_v1/backend/ls_iMotorSoft_Srv01_demo.py`

### 2. Frontend apuntando por defecto a remoto

- En `astro/src/components/global.js`, `URL_REST` queda configurado con `URL_REST_PRO`.
- Esto hace que el frontend pueda pegarle al backend remoto por defecto.

Impacto:

- Riesgo de probar en entorno incorrecto.
- Riesgo de confundir debugging local con comportamiento remoto.

Referencia:

- `SrvRestAstroLS_v1/astro/src/components/global.js`

### 3. Deriva de documentacion tecnica

- La guia de arquitectura menciona `Python 3.13`.
- El `pyproject.toml` del backend declara `requires-python = ">=3.12"`.

Impacto:

- Baja severidad, pero genera ruido operativo y falsas suposiciones en setup local o CI.

Referencias:

- `SrvRestAstroLS_v1/docs/README_ARQUITECTURA.md`
- `SrvRestAstroLS_v1/backend/pyproject.toml`

### 4. Senal mezclada en package manager

- El workspace visible usa `pnpm`.
- Existe ademas un `package-lock.json` vacio en la raiz, sin `package.json` raiz asociado.

Impacto:

- No rompe por si solo, pero ensucia la convención y dificulta ver rapido cual es el package manager canonico.

Referencias:

- `pnpm-workspace.yaml`
- `pnpm-lock.yaml`
- `package-lock.json`

## Lectura general del proyecto

El proyecto tiene una base mas ordenada de lo que parece a primera vista.

### Stack

- Backend: Python + Litestar + `uv`
